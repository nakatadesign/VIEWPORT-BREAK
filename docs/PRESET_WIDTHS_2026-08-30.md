## 3. 640 を入れるかどうか

**入れる。ただし「実機の再現」ではなく「ブレークポイントの境界」として。**

- 430 と 768 のあいだが 338px も空いていた。ここは **Tailwind の `sm:`（640px）が効き始める帯**で、実務で崩れが出やすいのに一度も止まれなかった。
- 640 に**実機はほぼ無い**。だから「デバイス幅」として入れるのは筋が悪い。入れる理由は「自分の CSS の境界の内側と外側を 1 クリックで往復したい」という一点。tooltip にもそう書いた（`Tailwind sm の境界。実機ではなくブレークポイントの確認用`）。
- 480 / 600 も候補にしたが**見送った**。480 は現行機に対応が無く（旧 Android の名残）、600 は Material の medium 境界だが Tailwind を使う案件では出番が無い。**境界枠は 1 つに絞る**方が、プリセットが「実機の列」であるという読み方を壊さない。

## 4. 落とした候補と理由

| 候補 | 落とした理由 |
|---|---|
| 393 | 402 との差 9px。iPhone 15/16 は 402 の帯で代表できる（第 1 次改訂時点の判断） |
| 402 | **第 2 次改訂で除外。** 390 との差 12px で刻みが細かすぎる → §6.1 |
| 412 | 414 との差 2px。**同じレイアウトにしかならない**ので 414 に寄せた |
| 384 | 390 との差 6px。同上 |
| 440 | 430 との差 10px。大型 iPhone の帯として 430 に寄せた |
| 420（iPhone Air） | 414 と 430 に挟まれる。単独機種のために 1 枠は使わない |
| 480 / 600 | §3 のとおり |

**判断の基準を 1 つに揃えた: 「10px 前後しか違わず、同じレイアウトにしかならない幅は代表 1 つに寄せる」。** 第 1 次改訂ではこれで 768 以下が 7 枠になった。第 2 次改訂は**同じ基準を 402 にも当てた**（§6.1）。

## 5. 残る限界

- StatCounter は**解像度**の統計であって CSS viewport ではない。上表の値は DPR 1 換算で CSS viewport と一致する組み合わせを選んでいるが、統計側が物理解像度で集計している端末が混ざっている可能性は排除できない。
- 日本のシェアは iPhone 偏重で、Android 中心のサービスでは 360 の重みが上表より大きい。360 を先頭に残しているのはそのため。
- 402 は「これから増える」という予測に基づく採用で、シェアの実測ではなかった。**この予測込みの 1 枠が第 2 次改訂で外れた**（§6.1）。

# 第 2 次改訂 — 402 を外し、320 を通常プリセットへ（v1.3.0 / 2026-08-30）

- きっかけ: オーナー指示「402 を外す / 320 を通常プリセットに / 最小幅チェックボタンは撤去」および
  「最小幅が 320 と書いてあるのに 50 も指定できるのはおかしい」
- EVALUATION_MODE: hybrid（採否はシェア実数と刻み幅の基準、UI と下限は使い捨て Chrome での実測）
- 実測ログ: `evidence/preset-320-2026-08-30/`（`measure.py` / `out/measure.json` / `shots_floor.py` / `out/shots_floor.json` とスクリーンショット）

## 6.1 402 を外した理由

**390 との差が 12px しかなく、§4 で自分が立てた基準に反していた。**

第 1 次改訂は「10px 前後しか違わず、同じレイアウトにしかならない幅は代表 1 つに寄せる」という
基準で 393・412・384・440 を落としている。**402 はこの基準に当てはめれば落ちる側だった。**
それでも残したのは「iPhone 17 世代でこれから最も増える」という予測を根拠にしたからだが、

- 390（iPhone 12–14）との差 12px は、**メディアクエリの境界をまたぐ幅ではない**。402 で崩れて 390 で崩れない CSS はまず書けない。
- シェアの実測値は無く（§2.1 の表に 402 は出てこない）、採用根拠が予測だけだった。
- 402 を残すと 768 以下が 7 枠になり、3 列グリッドが半端な行で終わる。

**予測 1 件のために基準を曲げていた、というのが実態。** 基準の側を通した。
iPhone 15/16/17 世代（393 / 402）は **390 の帯で代表させる**。

## 6.2 320 を通常プリセットへ昇格した理由

**320 は「実機シェア」の列では説明できないが、「レスポンシブ設計の下限」としては現役だから。**

- 320 は iPhone SE 第 1 世代 / 5s の論理幅。**実機としては役目を終えている**（§2.1 のシェア表に出てこない）。
- 一方で **CSS を書く側の下限としては 320 が実務値**として生き続けている。Bootstrap の最小サポート幅、
  WCAG 1.4.10 Reflow が要求する 320 CSS px、多くのデザインシステムのモバイル最小カラム幅がここに揃う。
  「320 で崩れないこと」は今も納品条件になる。
- つまり 320 は**他の 11 枠と役割が違うのではなく、「基準が実機シェアではなく設計要件」という点だけが違う**。
  640（Tailwind `sm` の境界）を実機ではない枠として並べているのと同じ扱いにできる。
  640 を通常プリセットとして並べておきながら 320 だけ別枠にする理由が無かった。
- 402 が抜けた穴にそのまま入り、**12 枠 = 3 列 × 4 行ちょうど**に収まる。

## 6.3 「最小幅チェック」ボタンを撤去した理由

**320 が通常プリセットに入った時点で、押す先が同じボタンが 2 つ並ぶことになるため。**

第 1 次改訂までの最小幅チェックボタンは `PRESETS` の `kind:'stress'` エントリで、
`w: 320` を **通常プリセットと同じ `apply(320)` に渡していただけ**（`popup.js` の `buildGrid`）。
違いは見た目（最終行ぶち抜き・淡色・`::before` のラベル）だけで、動作は完全に同一だった。
320 が通常枠に入るなら、残しても「同じ幅を 2 か所から押せる」以上の意味を持たない。

撤去したのは以下の 3 か所。ロジックの分岐はこれで無くなった。

| ファイル | 消したもの |
|---|---|
| `core.js` | `{ w:320, kind:'stress' }` エントリ（320 は通常枠の先頭へ移動） |
| `popup.js` | `if (p.kind === 'stress') b.classList.add('is-stress')` |
| `popup.css` | `.grid .btn.is-stress` と `.grid .btn.is-stress::before`（`content: "最小幅チェック"`） |

副次的な効果として、**この「最小幅チェック」という語がオーナー指摘の混乱源だった**（§6.4）。

## 6.4 「最小幅が 320 と書いてあるのに 50 も指定できる」— 何が食い違っていたか

**結論: docs は一度も「入力の下限は 320」と書いていなかった。書いてあったのは 320 プリセットの
役割名「最小幅チェック」で、これが「最小幅 = 320」と読めていた。**

指摘の時点で「320」と「最小幅」が同じ行に出ていたのは次の 3 か所で、いずれも**プリセットの
ラベル**であって入力バリデーションの話ではなかった。

| 場所 | 当時の記述 |
|---|---|
| `popup.css` | `content: "最小幅チェック"`（320 ボタンの接頭ラベル） |
| `PRESET_WIDTHS_2026-08-30.md` §1 | 「320 … **最小幅チェック枠**」 |
| `extension/README.md` | 「最終行の**最小幅チェック 320**」 |

**つまり食い違いは「実装 vs docs」ではなく「ラベルの語感 vs 実際の下限」だった。**
§6.3 で「最小幅チェック」という語ごと撤去したので、この読み違いの原因自体は無くなっている。
そのうえで、実際の下限を経路別に実測した。

## 6.5 実際の下限 — 実測（使い捨て Chrome / Chrome 151.0.7922.174）

下限は**ひとつではない。経路ごとに 4 つある。**

| # | どこの下限か | 値 | 性質 |
|---|---|---|---|
| 1 | **AppleScript（native host が使えるとき）** | **技術的な下限は見つからなかった（1px まで到達）** | Chrome / macOS 側の制約ではない |
| 2 | **native host `viewport_deck_host.py`** | **50px**（`MIN_WIDTH`） | **我々が置いた安全弁** |
| 3 | **popup の任意幅入力** | **50px**（`min="50"` + JS の `v >= 50`） | **我々が置いた安全弁** |
| 4 | **拡張 API フォールバック（host 無し）／ユーザーのドラッグ** | **500px** | Chrome 側の本物の下限 |

> [!warning]
> **#2 と #3 の 50px はこの節を書いた時点の値。第 3 次改訂で 1px に下げた（§6.9）。**
> 以下の測定はすべて 50px 時点のもので、記録としてそのまま残してある。

### 6.5.1 AppleScript 経路 — 1px まで下限が無い

使い捨てプロファイルの Chrome ウィンドウ 1 枚に対し、native host と同じ
`set bounds of window id N` を発行し、AppleScript の読み返し・CDP `Browser.getWindowBounds`・
`window.outerWidth` / `innerWidth` の 4 系統で読んだ（`out/measure.json` の `sweep_applescript`）。

| 要求 | 500 | 400 | 320 | 200 | 100 | 50 | 40 | 30 | 20 | 10 | 5 | 1 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| AppleScript 読み返し | 500 | 400 | 320 | 200 | 100 | 50 | 40 | 30 | 20 | 10 | 5 | **1** |
| CDP ウィンドウ幅 | 500 | 400 | 320 | 200 | 100 | 50 | 40 | 30 | 20 | 10 | 5 | **1** |
| `outerWidth` / `innerWidth` | 同上 | 同上 | 同上 | 同上 | 同上 | 同上 | 同上 | 同上 | 同上 | 同上 | 同上 | **1** |

**12 段階すべて ±0 で一致。クランプは一度も起きなかった。**
`WINDOW_FLOOR_2026-08-30.md` §5.1 は「50px（それ以下は未試行）」で止めていたが、
今回 **1px まで下ろしても Chrome も AppleKit も止めに来ないことを確認した**。
**この経路には実質的な下限が無い。**

### 6.5.2 では 50 という値は何なのか — 「ウィンドウを閉じられる下限」

技術的な下限が無い以上、`MIN_WIDTH = 50` は Chrome の制約ではなく我々の安全弁である。
**その値が妥当かを実写で確かめた**（`out/win-*.png`、`example.com` を開いた通常ウィンドウ）。

| 幅 | ウィンドウとして何ができるか |
|---|---|
| **320** | **全機能。** タブ・タブの `×`・`+`・戻る・再読込・omnibox（`exa…`）・★・`»`・`⋮`・信号機 3 つすべて到達可能 |
| 200 | タブストリップが `v`（タブ一覧）に畳まれる。omnibox は `ex…`。★ `»` `⋮` は消える。信号機・`+` は残る |
| 100 | **omnibox が消える。** 戻る・再読込・タブの `⋮` `×`・信号機のみ |
| **50** | 戻るボタンのみ。信号機は**赤・黄までが可視で緑は切れる**。**閉じるボタンにはまだ届く** |
| 20 | 赤ボタンも半分欠ける。**マウスでウィンドウを閉じられない** |

**50px は「マウスでウィンドウを閉じられる最後の幅」にほぼ一致する。**
偶然だが、安全弁として置くには筋の通った値だった。50 を下回るとユーザーは
AppleScript / CLI を打つ以外にウィンドウを元に戻す手段が無くなる。

### 6.5.3 拡張 API フォールバック — 500px でクランプ（既知の再確認）

host が使えないときに通る `chrome.windows.update` と同じ経路（CDP `Browser.setWindowBounds`）を掃いた
（`out/measure.json` の `sweep_cdp_api`）。

| 要求 | 640 | 520 | 500 | 480 | 430 | 375 | 320 | 200 | 100 | 50 |
|---|---|---|---|---|---|---|---|---|---|---|
| 実際の幅 | 640 | 520 | 500 | **500** | **500** | **500** | **500** | **500** | **500** | **500** |

**500 ちょうどは通り、480 以下はすべて 500 に張り付く。** `WINDOW_FLOOR_2026-08-30.md` の
500 DIP 下限を、今回のビルド（Chrome 151.0.7922.174）でも再確認した。

### 6.5.4 バリデーションの実挙動（popup 実描画で確認）

| 操作 | 結果 |
|---|---|
| 任意幅に `49` を入れて適用 | **適用されない。** ウィンドウ幅は変わらず（320 のまま）、`msg` も空 |
| 任意幅に `50` を入れて適用 | **適用される。** ウィンドウが実際に 50px になり、`msg` は `50px` |
| host CLI `viewport_deck_host.py 49` | `{"ok": false, "error": "幅は 50〜8000 の範囲で指定する: 49"}` / rc=1 |
| host CLI `viewport_deck_host.py 50` | `{"ok": true, "requested": 50, "bounds": {... "width": 50 ...}}` / rc=0 |

`49` のとき `msg` が空になるのは、`popup.html` の `min="50"` による **HTML 側の制約検証が
submit 自体を止める**ため。`popup.js` の `say('50〜4000 の整数を入れる。')` はこの経路では
到達しない（ブラウザ標準の吹き出しが出る）。**下限として機能はしているが、
下限を割ったときの説明文が二重に用意されていて片方が死んでいる。**

## 6.6 バリデーションを直すべきか（提案 — この節を書いた時点では未実装）

> [!note]
> **この節は提案時点の記録。オーナー決定は A・B・C のいずれでもなく「下限を 1 にする」だった。**
> 決定と実装は §6.9 を見る。以下は「何を比べて何を推していたか」を残すために原文のまま置いてある。

**推奨: 下限 50 は据え置く。UI と docs の表記だけ直す。** 理由は §6.5.2 のとおり、
50 が「マウスでウィンドウを閉じられる最後の幅」という実測の裏付けを持つため。

| 案 | 内容 | 評価 |
|---|---|---|
| **A（推奨）** | 下限 50 のまま。プレースホルダを `任意の幅` → `50〜4000` にし、README に「下限 50 の根拠は閉じるボタンが押せる限界」と書く | 実測の根拠に沿う。320 未満の崩れ確認という拡張の用途も残る |
| B | 下限を 320 に上げる | 指摘の語感には合うが、**320 は設計要件であってウィンドウの制約ではない**。320 未満を試す手段が消える |
| C | 下限を 200 に上げる（omnibox が残る限界） | 「ブラウザとして操作できる」を基準にすると筋は通るが、根拠が A より弱い |

あわせて、**下限を割ったときの説明が二重**（HTML 制約検証とブラウザ標準の吹き出し／`popup.js` の
到達しない `say()`）である点も、A を採るなら片方に寄せるのが素直。

**いずれもオーナー判断が要るため、この改訂では実装していない。**
`popup.html` の `min="50"` / `max="4000"`、`popup.js` の `v >= 50 && v <= 4000`、
host の `MIN_WIDTH, MAX_WIDTH = 50, 8000` は**今回いっさい変更していない**。

| 確認項目 | 実測値 | 判定 |
|---|---|---|
| プリセット数 | `12` | OK |
| 並び | `320 360 375 390 414 430 640 768 1024 1280 1440 1920` | OK（402 なし・320 が先頭） |
| グリッド | 3 列 × **4 行**（`gridTemplateRows` = `34.5px ×4`） | OK |
| `.is-stress` 要素 | `0` | OK（撤去済み） |
| `::before` の擬似要素テキスト | `[]` | OK（`最小幅チェック` ラベル消滅） |
| 本文に「最小幅チェック」 | `false` | OK |
| 行いっぱいのボタン | `[]` | OK |
| `320` をクリック | ウィンドウが実際に **320px**、`msg` = `320px`、`320` に `is-current` | OK（host 経路が実働） |
| ダークモード | `prefers-color-scheme: dark` で再描画 | OK（`out/02-dark.png`） |

スクリーンショット: `out/01-rest-light.png` / `out/02-dark.png` / `out/03-click-320.png` /
`out/04-custom-49.png` / `out/05-custom-50.png`

## 6.8 残る限界

- **1px まで到達したのは「ウィンドウのジオメトリがその値になった」ことの確認**であって、
  その幅で Chrome の UI が使えるという意味ではない。実用下限は §6.5.2 の実写で別に示している。
- 実測はすべて **macOS 15 / Chrome 151.0.7922.174 / 内蔵ではない 1920 幅ディスプレイ**の 1 台で取った。
  別解像度・別 DPR のディスプレイでの再現は取っていない。
- AppleScript 経路が下限を持たないのは `window_applescript.mm` が `bounds` を NSWindow へ
  KVC 転送しているためで（`WINDOW_FLOOR_2026-08-30.md` §5.2）、**Chrome の更新で塞がれうる**。
  塞がれた場合の下限は 500px（§6.5.3）になる。
- 320 を「設計要件としての下限」とする根拠（Bootstrap の最小サポート幅、WCAG 1.4.10 Reflow の
  320 CSS px）は**一般に知られた仕様上の値を根拠にしており、今回の dispatch では一次資料に
  当たり直していない**。§2.1 のようなシェア実数の裏付けとは性質が違う。

# 第 3 次改訂 — 任意幅の下限を 1px にする（v1.4.0 / 2026-08-30）

- きっかけ: §6.6 を読んだオーナーの決定「1px からにして。安全弁 50 は撤廃」
- EVALUATION_MODE: hybrid（下限の変更そのものはオーナー決定。**復帰できるかどうかだけは機械判定**）
- 実測ログ: `evidence/min1px-recovery-2026-08-30/`（`verify.py` / `shots.py` / `out/verify.json` / `out/shots.json` とスクリーンショット）

## 6.9 決定 — 下限 1、安全弁 50 は撤廃

**採ったのは §6.6 の A・B・C のどれでもない。「下限を 1 にする」という 4 つ目の案。**

### 50 を置いた経緯（残しておく）

- 50 は**最初から Chrome の制約ではなかった**。`viewport_deck_host.py` の `MIN_WIDTH` と
  `popup.html` の `min="50"` に我々が書いた値で、根拠は「これ以上狭いと壊れるかもしれない」
  という予防だった。
- §6.5.2 で**事後に**根拠を探し、「50px はマウスでウィンドウを閉じられる最後の幅」という
  実測と一致することが分かった。§6.6 で据え置きを推したのはこの一致を根拠にしている。

### 撤廃した理由

**50 は安全弁として機能していない。** §6.6 は「50 なら閉じるボタンに届く」を根拠にしたが、
**閉じられることと、拡張から幅を戻せることは別**で、後者はもっと手前で失われている。

今回の実写（`out/02-*.png`、背景を白ウィンドウで固定して撮影）:

| 幅 | ツールバーに残るもの | popup を開いて戻せるか |
|---|---|---|
| 320 | 拡張のパズルアイコンまで届く | **戻せる** |
| **50** | 信号機の赤・黄と戻るボタンだけ。**拡張アイコンは既に無い** | **戻せない** |
| 1 | 何も見えない。ウィンドウ枠が縦線 1 本 | 戻せない |

**50 に落ちた時点で「popup から戻す」はもう不可能だった。** つまり 50 は
「ここまでなら自力で復帰できる」線ではなく、単に「ここまでならマウスで閉じられる」線であり、
安全弁が守っているつもりだったものを実際には守っていなかった。**守れていない線を
下限として残す理由が無い。** 50 と 1 のあいだに、復帰可否の観点では差が無い。

そのうえで 1 を選ぶ側の利点は、§6.5.1 で確認済みの「AppleScript 経路には技術的な下限が無い」を
そのまま使えることだけ。**下限を設けるなら復帰手段とセットでなければ意味が無い**という結論に
なるので、下限を外して復帰手段を明示する側へ倒した（§6.10）。

### 変更したもの

| ファイル | 変更前 | 変更後 |
|---|---|---|
| `extension/host/viewport_deck_host.py` | `MIN_WIDTH, MAX_WIDTH = 50, 8000` | `MIN_WIDTH, MAX_WIDTH = 1, 8000` |
| `extension/popup.html` | `min="50"` | `min="1"` |
| `extension/popup.js` | `v >= 50 && v <= 4000` / `'50〜4000 の整数を入れる。'` | `v >= 1 && v <= 4000` / `'1〜4000 の整数を入れる。'` |

**上限は現状維持**（popup 4000 / host 8000）。§6.5.4 で指摘した「下限を割ったときの説明が
二重で片方が死んでいる」問題は今回いじっていない。下限が 1 になったことで `popup.js` 側の
`say()` に到達する余地はさらに狭まっており、**残る技術的負債として据え置く**。

## 6.10 復帰手段 — `--restore` を足した

下限を 1 にする条件として、**popup を経由しない復帰口を用意し、実際に戻せることを確認した。**

```bash
extension/bin/vw --restore        # 一番狭いウィンドウを 1280px へ
extension/bin/vw --restore 900    # 幅を指定
```

host に `restore_width()` と CLI の `--restore` / native message の `cmd:"restore"` を追加した。

**「現在のウィンドウ」ではなく「一番狭いウィンドウ」を対象にする。** これを打つ時点で
Chrome は前面ですらなく（ターミナルから打つため）、既存の `--get` が使う「先頭のウィンドウ」は
当てにならない。一方この経路が呼ばれる状況は常に「狭くしすぎた 1 枚がある」なので、
最狭を選ぶのが対象を名指しできる唯一の情報になる。

README には `## 戻し方 — 狭くしすぎて popup を開けなくなったとき` を独立した節として置いた。

## 6.11 実測 — 1px まで縮めて、そこから戻す

使い捨てプロファイルの Chrome（`Chrome/151.0.7922.174`）に `extension/` を
`Extensions.loadUnpacked` で読み込み、**popup の任意幅入力から実際に 1px まで縮めてから**
復帰を試した。オーナーの常用ウィンドウへ誤爆しないよう、起動前の window id を退避し、
`--restore` を呼ぶ前に毎回「最狭ウィンドウ == 使い捨てウィンドウ」を検証している
（`verify.py` の `restore_guard`）。実行前後でオーナー側のウィンドウは `500x847 @(100,30)` のまま変化なし。

| # | 手順 | 実測結果 | 判定 |
|---|---|---|---|
| 1 | popup の任意幅に `0` を入れて submit | `validity.rangeUnderflow = true`、ウィンドウ幅は 900 のまま | 弾かれる（期待どおり） |
| 2 | popup の任意幅に `1` を入れて submit | `msg` = `1px`、`window.outerWidth` = **1**、AppleScript 読み返し **1** | **1px に到達** |
| 3 | `viewport_deck_host.py --restore --json` | `{"ok":true,"restored_to":1280,"before":{...,"width":1},...}` / rc=0、読み返し **1280** | **戻せた** |
| 4 | 再度 1px にして `bin/vw --restore 900 --json` | `{"ok":true,"restored_to":900,...}` / rc=0、読み返し **900** | **戻せた** |
| 5 | host CLI `0` | `{"ok": false, "error": "幅は 1〜8000 の範囲で指定する: 0"}` / rc=1 | 境界が 1 に移った |
| 6 | host CLI `1` | `{"ok": true, "requested": 1, ...}` / rc=0 | 同上 |

スクリーンショット（`out/`、背景は同じ使い捨てプロファイルの白ウィンドウで固定）:
`01-window-1px-exact.png`（1px 幅のウィンドウそのもの）/ `02-a-820px.png` / `02-b-320px.png` /
`02-c-050px.png` / `02-d-001px.png` / `03-restored-800.png`。

**3 と 4 が通ったので下限 1 を入れた。** これが通らなければ入れずに止める、という条件だった。

## 6.12 残る限界

- **キーボードショートカット（`⌥⇧4` = 1280px）による復帰は未検証。** 理屈のうえでは
  `background.js` の `chrome.commands` 経路はウィンドウ幅と無関係に動くはずだが、
  1px のウィンドウへフォーカスを移す操作を含めて実測していない。README にも未検証と書いた。
- `--restore` の「最狭を選ぶ」は、**複数ウィンドウを意図的に狭くして並べている場合には誤爆する**。
  380px と 1px を並べていれば 1px 側が選ばれるので実用上は問題にならないが、
  「狭い方を残したい」ケースは想定していない。
- 実測は §6.8 と同じく **macOS 15 / Chrome 151.0.7922.174 / 1920 幅ディスプレイ 1 台**でのみ取った。
- 1px で「戻せる」ことは確認したが、**1px という幅そのものに実用価値があるかは検証していない**。
  §6.5.2 のとおりレンダリング結果を目視できる幅ではない。下限を開けたのは
  「安全弁として機能していない値を残さない」ためであって、1px での確認作業を推奨するものではない。
