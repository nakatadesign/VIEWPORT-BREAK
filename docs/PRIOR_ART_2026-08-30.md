## 1. 結論

### 1.1 三行で

1. **「Chrome 系の通常ウィンドウを 500px 未満にする」先行例は存在する。** ただし公開されている実現手段は **ブラウザ本体の改変**（Windows 版 `chrome.dll` のバイナリ書換／Chromium のソースパッチ再ビルド）**だけ**だった。
2. **「無改変の Chrome を、拡張・スクリプト・OS 操作だけで 375/390px にする」先行例は見つからなかった。** 記事・フォーラム・bug tracker で提示される回避策は、**すべて** DevTools でビューポートだけ縮める／ポップアップ窓へ逃がす／別ブラウザを使う、のいずれかだった。
3. **AppleScript `set bounds` が 500 DIP 下限を貫通する、と書かれた文献は見つからなかった。** ただしその土台となる 2 つの事実は**別々に公知**である（後述 §5）。したがって今回の成果は「未知の発見」ではなく **既知部品の未公開の組み合わせ**と判定する。**「世界初」とは書かない。**

## 2. 依頼 1 — macOS のウィンドウ管理アプリ

### 2.1 結論: どれも 500px 未満に到達できない。経路が Accessibility API だから

Rectangle / Magnet / Moom / BetterTouchTool / Amethyst / yabai / Raycast の window management は、**いずれも macOS の Accessibility API（`AXSize` / `AXPosition`）でウィンドウをリサイズする**。前提文書 §5.3 の実測どおり、この経路は 500px でクランプする。**「500px 未満に到達できる」と謳っている製品も、到達したという報告も、見つからなかった。**

### 2.2 根拠

**Rectangle**: Apple が公開 API を出していないため Accessibility API に依存している。作者自身が README で「Apple never released a public API for doing this」と書いている（Space 操作の文脈だが、Rectangle 全体が AX 依存であることは同 README のトラブルシューティングが `System Settings → Privacy & Security → Accessibility` の権限リセットを唯一の対処として挙げていることからも裏づけられる）。
→ https://github.com/rxhanson/Rectangle

**Raycast**: 公式 script-commands リポジトリの「Custom Window Size」は、**`System Events` 経由で `set size of window 1` している**。これは前提文書 §5.3 で 500 にクランプすると実測した、まさにその経路である。

```applescript
tell application "System Events" to tell application process frontApp
    set size of window 1 to {appWidth, appHeight}
```
→ https://github.com/raycast/script-commands/blob/master/commands/system/custom-window.applescript

**yabai**: そもそも「アプリが min/max サイズを持つ場合」を扱えていない。作者の issue #235 に、ウィンドウの制約を照会する API が無いため「リサイズ後の実フレームと要求フレームを比較して検出するしかない」と書かれている。**下限を貫通する仕組みは持っていない。**
→ https://github.com/koekeishiya/yabai/issues/235

**Moom / Magnet / BetterTouchTool / Amethyst**: 500px 未満への到達を謳う記述も、達成報告も見つからなかった。BetterTouchTool と Moom は AppleScript を実行する機能を持つため**アプリ側の `bounds` を叩く経路を組むこと自体は可能**だが、そのように使って Chrome を 500px 未満にした事例は見つからなかった（§5.2）。

**間接的な裏づけ**: Vivaldi フォーラムで、タイル型ウィンドウマネージャ（TWM）利用者が「この下限を回避する方法はあるか」と質問しているが、**誰も回答していない**。

> "Is there any way to get around this minimum? I use a TWM on a laptop and my screen is small enough that I run into situations where the window needs to be smaller than 500px a lot."（rtae）
→ https://forum.vivaldi.net/topic/48611/remove-or-allow-for-configurable-minimum-window-width

### 2.3 前提文書 N-3 への補足

前提文書は「Rectangle 実物での挙動は未実測（N-3）」としていた。**今回も実測はしていない**（停止線）。ただし、Rectangle が AX 依存であること・Raycast の公式スクリプトが `System Events` を使っていることが公開情報で確認でき、**「機序上ここに例外は無い」という前提文書の推定を支持する材料が増えた**。依然として実測ではない。

## 3. 依頼 2 — レスポンシブ確認用の開発者向けツール

### 3.1 結論: どれも「本物の Chrome ウィンドウ」を縮めていない

Sizzy / Polypane / Responsively App / Blisk は**すべて独立したアプリ**であり、複数の幅を**自分のウィンドウの内側**（iframe / Electron webview / 内蔵デバイスパネル）に並べて描画する。**Google Chrome のウィンドウを外から縮めるものは一つも無かった。** したがって「500px の壁を越えた先行例」には該当しない。

| 製品 | 実体 | 幅の作りかた | 本物の Chrome ウィンドウを縮めるか |
|---|---|---|---|
| **Sizzy** | Chromium ベースの独立アプリ（Electron / React） | **iframe の幅・高さ + `transform: scale()`**。作者本人が実装を説明している | **しない** |
| **Polypane** | Chromium を内蔵した Electron アプリ | 自ウィンドウ内に複数ペイン | **しない** |
| **Responsively App** | Electron 製の改造ブラウザ（OSS） | **Electron の webview を複数並べる** | **しない** |
| **Blisk** | Chromium ベースの独立ブラウザ | ウィンドウ内の「デバイス領域」。web content とデバイス領域の間のスプリッタをドラッグして幅を変える | **しない** |
| Viewport Resizer 等の拡張 | Chrome 拡張 | ページのビューポートだけを横に縮める（**ウィンドウは変えない**と明記） | **しない** |

### 3.2 根拠

- **Sizzy**: 作者 Kitze の紹介記事に「After tinkering with the width and height of the parent **iframe** and `transform:scale(zoom*0.01)` on the content」と実装が書かれている。
  → https://medium.com/@kitze/introducing-sizzy-a-tool-for-developing-responsive-websites-crazy-fast-39a8c0061992 / https://sizzy.co/
- **Polypane**: 「Polypane is an Electron app with the Chromium browser built in」。
  → https://sizzy.co/blog/polypane-vs-sizzy-vs-responsively/ / https://polypane.app/
- **Responsively App**: リポジトリ説明が「A modified web browser」。Electron の webview を複数使う構成。
  → https://github.com/responsively-org/responsively-app
- **Blisk**: 公式ヘルプが「resize the width of web content or the device content - simply drag the gray splitter」と説明しており、**ウィンドウ内の分割線**であってウィンドウ外形ではない。
  → https://blisk.io/questions/how-to-resize-device
- **CSS-Tricks の比較記事**（2020-09-01）も、これらを「別アプリ」対「ブラウザ拡張」という軸で整理しており、ウィンドウ外形を縮める製品としては扱っていない。
  → https://css-tricks.com/comparing-browsers-for-responsive-design/
- **Viewport Resizer**（拡張）: リポジトリ名からして「resize the website's viewport horizontally **without resizing the browser window**」。
  → https://github.com/mezzario/viewport-resizer-extension

### 3.3 これが今回の要件と噛み合わない理由

オーナー要件は「**開発中に常時見るウィンドウ**を 375px にする」であり、前提文書でポップアップ方式は既に不採用。上記 4 製品はいずれも「Chrome とは別のアプリに乗り換える」提案であって、**Chrome のタブ・拡張・プロファイル・DevTools をそのまま使い続けるという要件を満たさない**。「先行例」としては別カテゴリである。

## 4. 依頼 3 — 記事・フォーラム・Stack Overflow・GitHub issue・Chromium bug tracker

### 4.1 500 DIP 下限は 2010 年から知られている（未修正）

**Chromium issue 40439169（旧 54076）「can't resize window less than 500px width」** が現存する。報告本文（Chrome 5.0.375.99 / Ubuntu 10.04）を取得できた:

> **What steps will reproduce the problem?**
> 1. reduce manually the window under 500px wide
> 2. or through command-line "chromium-browser --geometry=320x240" for example
> **What is the expected result?** Render the windows as 320x240 px
> **What happens instead?** The minimum window width is 500px

→ https://issues.chromium.org/issues/40439169（旧 URL: https://bugs.chromium.org/p/chromium/issues/detail?id=54076 ）

**16 年後の現在も定数は 500 のまま。** `gh search code` で現行 Chromium ミラーを確認した:

```
chromium/chromium:chrome/browser/ui/views/frame/layout/browser_view_layout.h:
  static constexpr int kMainBrowserContentsMinimumWidth = 500;
```

> **注**: この issue の**コメント欄と現在のステータスは読めていない**。issues.chromium.org は JS アプリで、コメント取得エンドポイントがすべて 404 を返した（`/action/issues/<id>/comments` 等）。取得できたのは報告本文とタイトルのみ。関連する issue 875197「Chrome window minimum width is now absurdly high」は **HTTP 403**（非公開）で読めなかった。**「Google が WontFix にした」といった主張は、本調査では裏づけられていない。**

## 5. 依頼 4 — AppleScript `set bounds` で下限を割れる、は既知か（重点）

### 5.1 結論: 「AppleScript なら Chrome の 500px 下限を割れる」と書いた文献は見つからなかった

これが本調査で最も念入りに探した点である。日本語・英語の Web 検索、GitHub コード検索、Chromium 設計文書、AppleScript 系サイトを当たったが、**この事実を述べた記述は 1 件も見つからなかった。**

特に示唆的なのは次の 2 点:

- **AppleScript で Chrome をリサイズする記事は複数あるが、どれも大きいサイズしか扱っていない。** labnol（2013、Amit Agarwal）は `set the bounds of the first window to {...}` で Chrome をリサイズするスクリプトを配っているが、既定値は **1920×1080**。下限の話は一切出てこない。
  → https://www.labnol.org/software/resize-mac-windows-to-specific-size/28345
  同様に、よく参照される `resize-chrome.applescript` gist も **1440×900** を設定するだけ。
  → https://gist.github.com/saghul/8dcb138fe589a2255c9711b1b5873af2
- **GitHub コード検索で、狭い幅を AppleScript で Chrome に設定している例が 0 件だった。** 実行したクエリ（すべて 0 hit）:
  - `"set bounds of window 1" chrome 375`
  - `"tell application \"Google Chrome\"" "set bounds" mobile`
  - `chrome "windows.update" "native messaging" resize applescript`
  - `"contentMinSize" chrome 500 bypass`
  - `osascript "Google Chrome" "set bounds" 320`

  同じコード検索は `kMainBrowserContentsMinimumWidth` に対しては 20 件以上を正しく返しているので、**検索が機能していないのではなく、該当コードが公開されていない**と読める。

### 5.2 macOS 側から下限を割ろうとした人はいるが、AppleScript には辿り着いていない

- Vivaldi フォーラムの TWM 利用者の質問は未回答（§2.2）。
- BetterTouchTool / Moom / Raycast は AppleScript を実行できる。しかし**公式・コミュニティのスクリプトはいずれも `System Events`（AX）経由**であり（§2.2 の Raycast 公式スクリプトが典型）、アプリ側の `bounds` を叩く発想が出ていない。この 2 経路が Chrome 内部で別扱いになっていること（前提文書 §5.2 / §5.3）は、どこにも書かれていない。

### 5.3 ただし「部品」は 2 つとも公知である。ここが今回の判定の肝

今回の貫通は、次の 2 つの公知事実の**積**で説明できる。どちらも単体では新しくない。

**部品 A — Chromium の AppleScript `bounds` は NSWindow に転送される。** Chromium 公式の設計文書に明記されている:

> "The NSWindow associated with a browser can be used to get and set certain properties such as **bounds**, closeable, miniaturizable, miniaturized, resizable, visible, zoomable, and zoomed."
→ https://www.chromium.org/developers/design-documents/applescript/

（ただし同文書は**最小サイズ制約について一言も触れていない**。「だから下限を割れる」とは書かれていない。）

**部品 B — Cocoa の最小サイズはユーザー操作のリサイズにしか効かず、`setFrame:` は通る。** CocoaDev の「Overriding Limits On Window Sizes」に、まさにこの非対称性が実験結果として記録されている:

> "This code set the initial size correctly, but **resizing the panel with my mouse set the width back up to 59px**."
→ https://cocoadev.github.io/OverridingLimitsOnWindowSizes/

（AppKit 自身の 59px 下限の話だが、**「プログラムからの `setFrame:` は通る／マウスのリサイズは戻される」という挙動そのもの**が、前提文書 §5.2 が Chromium ソースのコメントから読み取った内容と同一である。前提文書 §6.5 で実測された「枠をドラッグすると 500 に戻る」も、これと同じ現象。）

**判定**: 部品 A と部品 B はどちらも公知。**しかしこの 2 つを掛け合わせて「AppleScript なら Chrome の 500 DIP 下限を割れる」と述べた文献は、探した範囲では見つからなかった。**

## 6. 依頼 5 — 今回作ったものは先行例に対して新しいのか

### 6.1 「通常ウィンドウを 500px 未満にする」先行例は 2 つあった。どちらもブラウザ本体を改変している

**先行例 1: Windows 版 `chrome.dll` のバイナリ書換（2022-03-25、日本語）**

「Chromium系バイナリ書換～横幅500px制限撤廃から始める快適ソシャゲライフ～」（髭山髭人）は、**Chrome / Chromium / SRWare Iron / CentBrowser の `chrome.dll` をバイナリエディタで書き換えて横幅制限を撤廃する**手順を公開している。用途はレスポンシブ開発ではなく「ブラウザソシャゲをスマホ幅で遊ぶ」こと。**通常のタブ付きウィンドウを任意の幅にできる、実在する先行例である。**
→ https://tech.packetroom.net/chromedll-binary-rewrite-sub-browser-howto

この記事の冒頭の一文は、本調査の結論そのものと一致する:

> 「Chrome(系)の横幅を500px未満に縮めるには **バイナリ弄るしか手立てがない**んで、それらに関する情報ポータル的な記事を用意しました」

つまり **2022 年時点で、この問題を 1 か月かけて解析した人間が「バイナリ書換以外に手が無い」と結論している。** AppleScript 経路は視野に入っていない（記事は Windows 前提）。

制約として記事自身が挙げているもの: 一部サブスク視聴サービスでエラーになる／Chrome の自動更新で改造が消える／実際の書換値は有料支援サイト側で配布（バージョンごとに変わる）。

**先行例 2: Chromium ソースパッチ（組み込み Linux 向け）**

Yocto レイヤ `OSSystems/meta-browser` に、定数そのものを下げるパッチが入っている:

```diff
- static constexpr int kMainBrowserContentsMinimumWidth = 500;
+ static constexpr int kMainBrowserContentsMinimumWidth = 480;
```
理由は 480×272 のパネル（TST043015CNHX）で Chromium を動かすため。**再ビルドが前提**で、480 までしか下げていない。
→ https://github.com/OSSystems/meta-browser/blob/master/meta-chromium/recipes-browser/chromium/files/0013-Reduce-minimum-browser-window-width-to-480px.patch

**先行例 3（参考・未検証）: Vivaldi は自ビルドから下限を外したらしい**

§2.2 と同じ Vivaldi フォーラムのスレッドが「Done」で締められており、最後の投稿（Pesala、Windows）が「The minimum window size is now a ridiculously useless **136x39 pixels**」と報告している。**Chromium 派生ブラウザが自ビルドで下限を撤去した例**にあたる。ただしこれは第三者の Windows 上の報告であり、**本調査では検証していない**（この機に Vivaldi は入っていない／停止線でインストール不可）。
→ https://forum.vivaldi.net/topic/48611/remove-or-allow-for-configurable-minimum-window-width

### 6.2 今回のものとの比較

### 6.3 判定

**「既知の組み合わせ」でも「世界初」でもない。次のとおり分けて述べるのが正確である。**

1. **達成目標（Chrome 系の通常ウィンドウを 500px 未満にする）は初ではない。** 少なくとも 2022 年にバイナリ書換で達成されており、組み込み向けにはソースパッチもある。**「世界初」と書いてはならない。**
2. **経路は、公開情報の中に先行例が見つからなかった。** 「ブラウザ本体を一切改変せず、AppleScript の `bounds` 経路で 500 DIP 下限を貫通する」という記述を、日本語・英語・GitHub コード検索のいずれでも発見できなかった。
3. **構成部品はすべて公知である。** Chromium の AppleScript が `bounds` を NSWindow へ転送すること（Chromium 公式設計文書）、Cocoa の最小サイズがユーザー操作にしか効かないこと（CocoaDev）、native messaging で拡張から外部プロセスを呼べること（Chrome 公式ドキュメント）— どれも新しくない。**新しいとすれば「この 3 つを繋いだこと」だけである。**
4. **したがって妥当な表現は「先行例は見つからなかった」であって「存在しない」ではない。** §7 の限界を必ず併記すべき。

対外的に書くなら、たとえば:
> 「Chrome 本体を改変せずに通常ウィンドウを 375px にする手順は、調べた範囲では公開されていなかった。同じ目的はバイナリ書換で達成されている先行例がある。」
